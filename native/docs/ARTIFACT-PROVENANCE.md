# GoreeCloud Search Native Development Artifact

## Status

This document describes a **Development** build/package evidence path for the GoreeCloud-owned native Search service.

It does not declare a GoreeCloud Search Release Candidate, production deployment, production approval, Stable qualification, target-host acceptance, live-provider acceptance, or complete platform conformance.

The authoritative application lifecycle remains `Development`.

## Purpose

The native Search source under `native/` must be able to produce an exact-revision runtime artifact whose identity can be verified independently of the mutable development branch that produced it.

`.github/workflows/goreecloud-native-development-artifact.yml` therefore establishes a bounded CI package-validation layer between source validation and any future release or target-environment acceptance.

The workflow is intentionally separate from the inherited SearXNG-derived container and historical first-Stable/RC publication paths. A SearXNG-derived image is not a native Search artifact merely because both implementations remain in the same migration repository.

## Exact revision boundary

For pull requests, the workflow explicitly checks out `github.event.pull_request.head.sha`. For pushes and manual runs it uses `github.sha`.

Before building, it verifies that:

- the checked-out Git `HEAD` equals the selected candidate SHA;
- the selected SHA is a canonical lowercase 40-character Git revision; and
- the working tree is clean.

A moving branch name is not accepted as artifact provenance.

## Native packages

`native/scripts/build-development-artifacts.sh` builds the native `searchd` command for:

- Linux amd64; and
- Linux arm64.

The build uses Go 1.25.x in the CI contract, `CGO_ENABLED=0`, `-trimpath`, VCS metadata, and stripped binary symbols. Each target is built twice and the two binaries must be byte-identical before packaging continues.

Each package contains:

- the `goreecloud-search` native executable;
- `BUILDINFO.txt` generated by `go version -m`;
- `ARTIFACT-METADATA.json`; and
- the repository AGPLv3 license.

The tar/gzip package is normalized for ordering, timestamps, ownership metadata, and gzip timestamps so the package boundary is deterministic for the same accepted binary and metadata inputs.

## Provenance evidence

The artifact bundle includes `artifact-provenance.json` and `SHA256SUMS`.

The provenance record identifies:

- GoreeCloud Search / `native-searchd`;
- authoritative source repository;
- exact source revision;
- Go toolchain identity;
- Linux/amd64 and Linux/arm64 artifact names and SHA-256 digests;
- lifecycle `development`;
- artifact scope `ci-development-candidate`;
- `production_approved: false`;
- `release_candidate_declared: false`;
- `target_environment_validated: false`;
- `live_provider_acceptance_validated: false`; and
- platform conformance `nonconformant`.

Those negative fields are deliberate evidence boundaries. Packaging must not silently upgrade application maturity.

## Packaged runtime acceptance

The workflow extracts the Linux/amd64 package and launches the packaged executable on a GitHub-hosted Linux runner using a loopback-only address.

It validates the exact VCS revision embedded by the Go toolchain and exercises the packaged process through:

- `/healthz`;
- `/api/v1/status`;
- `/api/v1/readiness`;
- `/api/v1/providers/definitions`;
- the native homepage;
- Preferences; and
- a specialized Images API request with zero configured providers, which must fail closed as not implemented rather than inventing provider coverage.

The runtime must continue to report `production_approved: false`, canonical lifecycle `development`, local-native readiness scope, zero configured providers, and no credential exposure.

This establishes **build/package validation plus CI-Linux packaged-runtime acceptance** for the exact revision. It is not target-environment validation.

## Configuration and secret boundary

The package contains no production provider configuration, provider credentials, reusable secret, target-host reverse-proxy configuration, private DNS configuration, NetBird configuration, monitoring credentials, backup material, or production authorization.

Runtime providers remain deployment-controlled through `GOREECLOUD_SEARCH_PROVIDER_CONFIG_FILE`. Optional bearer credentials remain environment references resolved at runtime by the provider loader and must not be copied into source, artifact metadata, CI evidence, or ordinary deployment documentation.

The native service continues to default to `127.0.0.1:8080` unless `GOREECLOUD_SEARCH_ADDR` is explicitly set. This CI artifact does not establish an approved non-loopback production binding.

## Relationship to Release Candidate and production

A Development artifact may later become input to Release Candidate review, but the workflow does not perform that promotion.

Before a native Search artifact can be treated as a Release Candidate or used for controlled incumbent replacement, the applicable GoreeCloud lifecycle and production-readiness requirements still require an identifiable accepted candidate scope and sufficient evidence for provider/category behavior, current Stable Glaze UI application acceptance, Privacy Shield, Wardveil Security, Everkeep recovery/rollback, applicable Identity/Mesh/Manager integration, target-host networking and monitoring, migration compatibility, and other release blockers.

Before production cutover, the exact deployed artifact must be proven to match the separately approved candidate and the previous known-good transitional runtime must remain recoverable until rollback requirements are satisfied.

## Retention

The CI workflow uploads the Development artifact evidence for 90 days. Artifact retention is useful build evidence, but a GitHub Actions artifact is not the authoritative source repository, an independent Everkeep backup, a production release registry, or a permanent release record.
